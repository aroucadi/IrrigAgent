# Feature Specification: Internal Engagement & Traction Dashboard

**Feature Branch**: `018-internal-traction-dashboard`

**Created**: 2026-07-31

**Status**: Draft

**Input**: User description: "Create a new feature spec — do not modify any existing farmer-facing feature or messaging flow. This is an internal, founder-only tool, entirely separate from the WhatsApp product surface, built to turn already-captured engagement data into something screen-shareable in packing-house discovery calls. Feature name: Internal Engagement & Traction Dashboard (Sales Evidence Tool)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Read-only engagement summary from existing Firestore data (Priority: P1)

As the founder preparing for a packing-house discovery call, I want to run a standalone local tool that queries existing Firestore interaction logs and outcome-feedback records to generate a clear, screen-shareable summary of active farms, advisory response rates, and irrigation override behavior, so that I can present real pilot evidence instead of anecdotal claims.

**Why this priority**: High-impact sales evidence tool directly needed for enterprise buyer discovery calls. It unlocks credibility without risking production app stability or modifying farmer-facing flows.

**Independent Test**: Can be executed locally via command line against existing Firestore collections without running the FastAPI service or modifying any production database records. It outputs a formatted local report and chart image cleanly displaying current engagement metrics with mandatory small-sample directional labels.

**Acceptance Scenarios**:

1. **Given** existing Firestore collections containing farm profiles, irrigation recommendations, and outcome feedback records, **When** the founder executes the report generation tool locally, **Then** the system queries Firestore read-only (zero database writes) and calculates total registered farms, 7-day and 30-day active farms count, daily advisory response rates, and outcome-feedback breakdown percentages (`Followed`, `Less`, `More`, `Skipped`, `No-response`).
2. **Given** a dataset where a reporting time period contains fewer than 5 active farms, **When** the summary report is generated, **Then** the output explicitly and prominently displays an "early/directional data" label on all relevant charts and metrics for that period.
3. **Given** the generated output, **When** reviewing metric labels and narrative summaries, **Then** the report presents raw engagement numbers and self-reported override rates only, making zero claims regarding unmeasured outcomes such as water savings or yield improvements.

---

### User Story 2 - Exportable report for post-meeting leave-behinds (Priority: P2)

As the founder following up after a discovery call, I want to export the engagement summary as a static high-resolution PNG image or PDF document, so that I can send it as an email attachment or leave-behind artifact.

**Why this priority**: Important for sales collateral and follow-up communication after live screen-share sessions.

**Independent Test**: Can be tested by invoking the export capability after report generation and verifying that a clean, well-formatted PNG/PDF artifact is produced on local disk using standard project dependencies.

**Acceptance Scenarios**:

1. **Given** an engagement summary generated by the tool, **When** the export function is triggered, **Then** a static PNG or PDF file is generated locally containing all charts, metric cards, and small-sample directional labels formatted for standard viewing/printing.
2. **Given** chart generation requirements, **When** building export artifacts, **Then** the tool reuses existing project visualization dependencies (such as `matplotlib`) without introducing external paid reporting or rendering services.

---

### Edge Cases

- What happens when Firestore contains zero recorded farm interactions or outcome feedback entries? The tool MUST render a clean empty-state report labeled clearly as "No Pilot Data Recorded" without crashing or throwing unhandled null pointer exceptions.
- What happens when Firestore network connection fails or credentials are missing? The tool MUST report a concise, actionable error message to stdout and exit cleanly without creating partial export files.
- What happens when active farm counts fluctuate above and below 5 active farms across different weekly buckets? The tool MUST dynamically apply the "early/directional data" warning label only to the specific buckets/periods with under 5 active farms.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST operate as an isolated, standalone local script/tool that executes completely outside the FastAPI production application process.
- **FR-002**: System MUST perform exclusively read-only queries against existing Firestore collections (`farms`, `recommendations`, `outcome_feedback`, `interaction_logs`) with zero write operations.
- **FR-003**: System MUST calculate total registered farms, active farms in the last 7 days (replied to at least one advisory or sent at least one message), and active farms in the last 30 days.
- **FR-004**: System MUST calculate historical response rates to daily advisories over daily/weekly time periods.
- **FR-005**: System MUST compute the percentage distribution of outcome-feedback responses across all 5 standard categories: `Followed`, `Less`, `More`, `Skipped`, and `No-response`.
- **FR-006**: System MUST automatically evaluate sample size for every reported time bucket and visually tag any period with fewer than 5 active farms with an explicit "early/directional data" warning.
- **FR-007**: System MUST render the summary output into a clean, screen-shareable visual format (such as a static matplotlib chart figure or local static HTML page).
- **FR-008**: System MUST support exporting the visual report as a high-resolution PNG image file and/or PDF document to a specified local directory.
- **FR-009**: System MUST strictly restrict metric presentation to raw engagement counts and self-reported override ratios, omitting any speculative or unverified yield/water savings metrics.

### Key Entities

- **Farm Engagement Metrics**: Aggregated count of registered farms, 7-day active farms, and 30-day active farms derived from Firestore timestamp logs.
- **Advisory Response Rate**: Percentage ratio of sent daily advisory recommendations that received a farmer response within 24 hours.
- **Outcome Feedback Breakdown**: Proportional distribution of recorded feedback decisions (`Followed`, `Less`, `More`, `Skipped`, `No-response`).
- **Sample Size Tag**: Governance metadata attached to aggregated time buckets indicating whether active sample size meets statistical authority thresholds (minimum 5 active farms).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Executing the reporting tool against current pilot Firestore data produces a correct, complete summary report in under 10 seconds locally.
- **SC-002**: All reporting periods with fewer than 5 active farms are 100% reliably flagged with an explicit "early/directional data" label in generated visual outputs.
- **SC-003**: Generated report images (PNG/PDF) are exported with crisp resolution suitable for screen sharing in discovery meetings and PDF email attachments.
- **SC-004**: Implementation introduces exactly 0 code modifications to any existing production or farmer-facing files (including `app/decision.py`, `app/main.py`, and WhatsApp webhook handlers).

## Assumptions

- Firestore service account key or local GCP default application credentials with read permission to existing pilot collections are available in the local execution environment.
- Python 3.11 environment with existing project visualization packages (`matplotlib`) is available locally.
- 7-day and 30-day activity definitions count any incoming WhatsApp interaction or advisory response log entry in Firestore as active engagement.
- Exported report files will be written to a local gitignored `output/` directory by default.
